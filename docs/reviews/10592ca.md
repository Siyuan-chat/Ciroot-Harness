## 新发现

### F12：未翻完页面却标 complete（P1，A13/A27）

给 OpenAlex 返回基本分页 fixture：`meta.count=3,page=1,per_page=2`，含两个结果，无 next_cursor。适配器既未请求 `cursor=*`，也不接受 page/cursor 输入，却因 next_cursor 缺失返回 `completeness=complete,continuation=null`。正常第一页因此可能被当成全部结果，影响覆盖报告及完整水位。

按来源契约实现分页输入/输出和可恢复 continuation；只有已确认遍历完成才 complete。候选或预算上限截断时保存 partial 和下次可用状态。当前官方资料区分基本分页与 cursor 分页，cursor 模式须显式启动并传递返回游标：[OpenAlex 分页文档](https://help.openalex.org/api/paging/)。测试应覆盖基本分页截断、游标多页、空完成页和预算耗尽，不只人为提供 next_cursor。

### F13：EPO 凭据存在但没有参与认证（P1，A14）

传入合成 key/secret 后，适配器只发出一次 GET；没有 token 请求，headers 只有 Accept，没有 Authorization。它仅检查环境变量非空而不使用凭据，并返回 raw_xml 而非可分析 candidates。该实现无法完成约定的认证检索流程。

请实现 OAuth client-credentials 令牌获取与缓存/到期处理，使用 Bearer token 请求检索资源；将 XML 转成统一候选、公开编号/kind、族与分页信息。参考 [EPO OPS v3.2 参考指南 §2.3.2](https://link.epo.org/web/searching-for-patents/data/en-ops-v3.2-documentation-version-1.3.20.pdf)。同时依照既定 M3 实现正文/claims/description 的分开覆盖，不把 raw_xml 返回值当 A14 已完成。

### F14：异常暴露敏感请求内容，响应错误未统一（P1，A05/A15/R22）

向 requests 注入包含合成 `api_key` URL 的 ConnectionError，`str(SourceError)` 仍含该合成凭据。原因是直接使用 `str(exc)`；真实 requests 错误可能含查询 URL。应用日志或异常输出会沿用它。请产生不含敏感 URL/header/body 的结构化错误，并处理异常链/诊断路径，保留可用的错误类型和安全上下文。不要只替换测试用 sentinel。

200 响应的 JSON 根为数组会抛 AttributeError，非法 JSON 会抛 JSONDecodeError；均未转换为 `SourceError(kind=invalid_response)`。将 JSON 解码、顶层/字段类型验证纳入适配器错误边界，使单来源坏响应能被统一处理。重试/限流与共享预算仍按 M3/F01 完成。
